## Project Overview

leptos-routes provides declarative, type-safe route definitions for the Leptos web framework via procedural macros. Users declare routes as nested modules with `#[route(...)]` attributes inside a `#[routes]`-annotated module, and the macros generate route structs, a `Route` enum, and optionally a full router component.

## Build & Test Commands

```bash
# Build the entire workspace
cargo build --all

# Run all tests
cargo test --all

# Run a single test by name (tests are in leptos-routes-macro/tests/)
cargo test -p leptos-routes-macro <test_name>

# Check without building
cargo check --all

# Lint (pedantic)
cargo clippy --all -- -W clippy::pedantic
```

## Workspace Structure

Two crates in a Cargo workspace:

- **`leptos-routes`** — Public-facing crate. Re-exports all macros from `leptos-routes-macro`. Users depend on this crate.
- **`leptos-routes-macro`** — Proc-macro crate containing all implementation logic.

## Macro Crate Architecture (`leptos-routes-macro/src/`)

Entry points in `lib.rs`:
- `#[routes(...)]` — Top-level attribute macro applied to a module. Parses the module hierarchy and generates route structs, enum, and optionally a router. Views are generated by default when `fallback` is provided; use `without_views` to opt out. Accepts optional `path = "/..."` for root path prefix. Supports `layout!()`, `index!()`, and `page!()` directly in the module body (creates a synthetic root `RouteDef`).
- `#[route(...)]` — Attribute macro on nested sub-modules. Takes a path string (e.g., `"/users/:id"`). Components are declared via `layout!()`, `index!()`, and `page!()` body macros inside the module.

Key modules:
- **`route_macro_args.rs`** — Parses `#[route(...)]` path attribute.
- **`route_def.rs`** — `RouteDef` struct and `collect_route_definitions()` which recursively walks the module tree to build the route hierarchy.
- **`path.rs`** — Parses path strings into segments (`Static`, `Param`, `OptionalParam`, `Wildcard`). `ParamInfo` collects parameters through the route hierarchy for `materialize()` method signatures.
- **`module_path.rs`** — Tracks the current position in the module nesting.
- **`util.rs`** — `to_pascal_case()` (snake_case module → PascalCase struct name), `sanitize_identifier()` (escapes Rust keywords).
- **`generate/`** — Code generation:
  - `mod.rs` — Orchestrates generation, injects `clippy::module_inception` allow.
  - `route_struct.rs` — Generates a struct per route with `path()` and `materialize()` methods. Nested routes call their parent's `materialize()`.
  - `all_routes_enum.rs` — Generates `Route` enum with a variant per route.
  - `router.rs` — When views are enabled (i.e. `without_views` is not set), generates `route_tree()` returning JSX-like Leptos router markup and `router()` which wraps `route_tree()` in `<Router>` for convenience. Validates that leaf routes have views. Parent routes may optionally use `layout!()` (wraps children with `<Outlet/>`) and `index!()` (shown when the route is matched directly). Parent routes without `layout!()` get an implicit passthrough `<Outlet/>`.

## Testing

### Assertion style

All tests (both unit and integration) use the `assertr` crate's `assert_that!()` macro instead of std `assert!`/`assert_eq!`/`assert_ne!` macros. Common patterns:

```rust
use assertr::prelude::*;

assert_that!(value).is_equal_to(expected);
assert_that!(value).is_not_equal_to(other);
assert_that!(flag).is_true();
assert_that!(flag).is_false();
assert_that!(vec).is_empty();
assert_that!(slice).has_length(3);
assert_that!(slice).contains(element);
assert_that!(option).is_some();
assert_that!(option).is_none();
assert_that!(string).ends_with("suffix");
assert_that!(string).starts_with("prefix");
```

### Integration tests (trybuild)

Tests use `trybuild` for compile-time testing. The test harness is `leptos-routes-macro/tests/progress.rs` which runs numbered test files. Each test file defines a `#[routes]` module and asserts on the generated output. Tests require `ssr` feature on `leptos`/`leptos_router`.

Tests are grouped by number range:
- **01-09**: Core struct generation (pass tests)
- **10-18**: View rendering and extended struct tests (pass tests)
- **20-26**: `#[routes()]` attribute errors (compile-fail)
- **30-36**: `#[route()]` path validation errors (compile-fail)
- **40-48**: Body macro conflicts & duplicates (compile-fail)
- **50-55**: Structural/hierarchy errors (compile-fail)

Adding a new integration test:
1. Create a numbered `.rs` file in `leptos-routes-macro/tests/` in the appropriate group (e.g., `56-my-error-test.rs`).
2. Add a corresponding `t.pass(...)` or `t.compile_fail(...)` line in `progress.rs`.
3. For `compile_fail` tests, provide a matching `.stderr` file with expected error output.
4. To regenerate `.stderr` files after changing error messages, run tests with `TRYBUILD=overwrite cargo test -p leptos-routes-macro`.

### Unit tests

Unit tests live as `#[cfg(test)] mod tests` at the bottom of source files in `leptos-routes-macro/src/`. They test pure logic (parsing, tree traversal, string utilities) in isolation. Run with `cargo test -p leptos-routes-macro --lib`.

## Key Details

- Rust edition 2024, MSRV 1.88
- Route structs are unit structs with derived `Debug`, `Clone`, `Copy`, `PartialEq`, `Eq`, and `Hash`
- `materialize()` builds full URLs by recursively calling parent route materializers
- `path()` returns just the local path segment(s) for use in `<Route>` declarations
- Error diagnostics use `proc-macro-error2` (`abort!` macro) for user-friendly compile errors with spans
- The `use super::*;` import chain is critical: the root module injects macro imports (`route`, `layout`, `index`, `page`, `fallback`) and `use super::*;`, then each child module also gets `use super::*;` — this chains all imports downward so component references and macro names resolve at every nesting level
- `autotests = false` in the macro crate's `Cargo.toml` means tests are explicitly declared; the single `[[test]]` entry points to `progress.rs`
